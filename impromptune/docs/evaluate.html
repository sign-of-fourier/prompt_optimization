Evaluate

The terminal block on the canvas. It decides what “better” means, which makes it the most consequential thing you will configure.

Scorers

A scorer compares the terminal prompt's output with the row's label and returns a number. Pick the output field to compare, or leave it on whole output.

ScorerComparesUse when
Exact matchthe field equals the label, optionally normalizing case, punctuation and articlesclassification into known categories
Containsthe label appears somewhere in the outputthe answer is embedded in prose
Token F1word overlap with the labelshort free-text answers, QA-style
List (set F1)the items in the output against the items in the label, in any order, with credit for each one foundextraction: names, SKUs, line items, tags

Numericnumbers within a tolerance, relative (a share of the label) or absolute (in its units)quantities, where 4.99 and 5.0 are the same answer

LLM judge, no referencea judge model grades against a rubric alonethere is no single right answer — tone, helpfulness

You can add more than one. Each produces its own named metric, and they all land in the same vector.

Lists are scored as sets. “Charles, Nantucket”, “nantucket, charles” and a list field holding both names all score 1 against the label ["Charles", "Nantucket"]; finding one of the two scores 0.67. Declare the output field as a list where an item can contain a comma; text is split on commas, semicolons and new lines. The one choice to make is which mistake costs more: a missing item (screening, compliance, where a miss is expensive) or a wrong extra (anything that gets acted on automatically). Either way, the rewriter is told which items were missing and which were extra on each row it sees. Turn normalize off where case carries meaning, as in SKUs or tickers.

When one class dominates, score balanced. Exact match has a balanced option. It adds accuracy_balanced, which weights each row by how rare its label is, so every class counts equally: the average of per-class recall. Plain accuracy on a dataset where most rows are one class rewards a prompt that always answers that class. Put the objective weight on the balanced metric instead.

A judge costs money and has opinions. Every judged row is an extra model call on every evaluation of every candidate, and the judge's bias becomes the thing you optimize. Where an exact-match scorer will do, it is cheaper, faster and more honest.

Choosing a scorer, and when to reach for a judge

Start from what the terminal prompt returns. Most projects never need anything below the fourth row.

Before adding a judge, tighten the output. A judge is often the fix for a format problem that a field would solve for free. If the label is one of six queues, list them as the field's allowed values. If it is several names, make the field a list. If it is a number, make the field a number. Normalization (case, punctuation, articles) belongs in the scorer, where it is free and exact, not in the prompt, where the optimizer may rewrite it away.

The sign you need one: the pilot or a baseline run shows rows marked wrong that you would mark right. “45” against a label of “45 days”, or “as account credit only” against “account credit”. Read ten failed rows before deciding. If most of them really are wrong, the scorer is fine and the prompt is the problem.

Using a judge well

  • Give it the label. A judge that compares against a reference is far steadier than one asked whether an answer is good. Use the no-reference judge only when there is genuinely no right answer.
  • Write the rubric as the rule for “the same answer”. “The same number of days, whatever the wording” beats “Is this correct?”.
  • It is frozen. The judge's model and rubric are never rewritten by the optimizer. That is deliberate: a judge that could change would be optimized into agreeing.
  • Keep a strict scorer beside it. Exact match and a judge can both be in the vector. Weight the judge for meaning; keep the strict one to watch format, or to weigh it a little if downstream code needs the exact form.
  • Check it before you trust it. Run a baseline run, open twenty or thirty rows, and mark each verdict right or wrong yourself. If you disagree with the judge on more than a couple, fix the rubric before spending on a run. The optimizer will chase whatever the judge rewards, mistakes included.
  • Expect some noise. A model judge at temperature 0 does not always give the same verdict twice, so a judged score moves a little between identical evaluations. Treat small differences between candidates as noise, and read the hold-out before believing a gain.
  • It is billed per row, per evaluation. Every candidate's full evaluation calls the judge once per row. The cost projection counts it.
Jev judge (beta, by invitation). Jev is a small model that answers a yes/no question with a probability instead of a sentence: “is the model answer the same as the label?” comes back as 0.93, not a verdict. It answers in a fraction of a second, so it can be asked on every row, and in bpto's first comparison it separated right from wrong answers better than a general model asked for a score, and gave the same probability twice. That comparison is small, so during the beta Jev is recorded, not optimized: it scores every row next to your own scorers, its weight stays at 0, and a row Jev cannot answer is counted in jev_match_failed instead of failing. Use a run to see where it disagrees with your strict scorer, and check those rows yourself.

The metric vector

A run does not reduce a row to one number. Alongside your scorers it records how the program behaved:

  • template_tokens — the prompts themselves, summed over prompts. This is the recurring bill.
  • prompt_tokens and output_tokens — rendered with the data, and what came back.
  • steps — how many prompt calls the row took, which matters when there are loops.
  • parse_fail.* — per prompt, how often structured output could not be parsed.
  • step.<id>.* — an external step's latency, cost, cache hits and failures.

Nothing is collapsed inside a scorer. The scorers report; the objective decides.

The objective

The objective is a set of weights over those metrics. accuracy: 1.0 alone means what it says. Adding a negative weight on template_tokens makes the search pay for length:

accuracy:        1.0
template_tokens: -0.002

At that weight, a prompt may spend ten extra tokens if they buy two points of accuracy, and not otherwise. Choosing the Compress goal in the optimizer sets this for you and asks the reflection model for shorter prompts that keep the same answers; it is the same machinery with a different weight and a different rewriting instruction.

The run also reports a Pareto front: the candidates that are not beaten on both accuracy and length at once. Reading the front is usually more useful than reading the winner — a prompt one point behind the best and half the length is frequently the one to ship, and only the front shows you it exists.

Pre-program step cost is reported, not traded off. Every candidate sees the same enriched rows, so a step's fetch cost is the same constant for all of them and shifts every score equally. What is optimizable is which of the step's fields are worth pasting into a prompt — pulling five fields and using two is a finding the compression objective will make for you.
