Programs and prompts

A program is made of prompts and the edges between them. It is what gets optimized.

A prompt

One node on the canvas, and the unit the optimizer rewrites. It has four things worth setting:

The template

What you would have typed into a chat box. Words in {braces} are placeholders, filled from the dataset's columns, from an earlier prompt's output field, or from an external step. A placeholder with no source is a blocking error before the run starts, not a surprise at row 40.

What it does

One line, in your words. This is not decoration: the reflection model reads it when deciding how to rewrite the prompt. A prompt described as “summarizes what the customer wants” gets rewritten differently from one described as “extracts the order number”.

Output fields

Prompts return structured fields, not loose text, so the next prompt and the scorer can pick one out by name. A field has a name, a type, and optionally a description the model sees. No fields means free text, which is fine for the last prompt if your scorer compares whole output.

Model and token cap

Each prompt can run on its own model; empty means the project default. Mixing is normal — a cheap model to classify, a better one to draft.

A prompt can be excluded from rewriting with rewritten by the optimizer. Turn it off for a prompt you have already settled, and the search spends its budget on the others.

Edges, and what they carry

An edge from A to B means B runs after A. Click it to say what B receives: each of B's placeholders can be mapped to one of A's output fields, or to $text for A's raw output. Anything not mapped is looked up in the dataset columns and in whatever earlier prompts on the path already produced.

A prompt with no outgoing edge is a terminal: its output is what Evaluate grades. The dashed line to the Evaluate block appears and disappears on its own to show you which prompt that currently is. The entry prompt is where a row starts; by default it is the first one you added, and you can move it.

Routers

A prompt with two or more outgoing edges is a router. It is still a prompt and it is still optimized; the only difference is that a next field is added to its output automatically, with one option per outgoing edge. The model returns the name of the edge to take.

  • Name the edges. Click each one and give it a short option name. The names are what the model chooses between, so they should mean something: needs_human, not option2.
  • Mark a default. One edge is taken when the model's next cannot be parsed. Without it, an unparseable answer is a failed row.
  • Say what the options mean. In the prompt template, in words. The option names alone are a guess.

Edges may loop back to an earlier prompt — a draft-and-revise cycle is two prompts and a router. That is what max prompt calls per example caps: without it, a program that keeps deciding to revise never finishes a row. Every row stops at the cap, and the cap is part of the cost projection.

When a project should be two projects

Big problems usually come apart along natural seams, and each piece optimizes better on its own dataset than the whole does on one label at the end. The studio has no “run this once per item” node, on purpose: the pieces are separate projects, and your code joins them.

A freight inbox, for example. One email can carry several loads, and each load needs a quote.

Project 1: find the loads

Input: the email. Label: the list of loads in it. Scorer: List, set to punish a missing load more than an extra one, since a missed load is lost business. Dataset: emails you have already worked, with the loads your team entered.

Project 2: quote one load

Input: one load's details. Label: the rate you quoted. Scorer: Numeric, with the tolerance you would accept. Dataset: past loads and their quotes, which you probably have far more of than emails.

In production your code calls the first project's served version, loops over the loads it returns, and calls the second for each. Each piece has its own version, its own hold-out number and its own cost, so when quotes go wrong you know which piece to look at.

Signs a project wants splitting:

  • A prompt produces a list, and each item needs more work of its own.
  • There is a middle output you could check by hand, and you have, or could write, labels for it.
  • The final label cannot tell you which prompt got it wrong. A run on a four-prompt chain with one label at the end spends its budget guessing where the failure is.
  • The pieces need different scorers: a list here, a number there.

Where each piece's labels come from: the records you already keep (entered loads, sent quotes, final routing), or a baseline run of the whole program, whose traces show every prompt's output for you to mark right or wrong.

When one project is right: routers and loops belong in one program, and so do prompts whose outputs only mean something together. If all you have is the label at the end, keep one project and optimize one prompt at a time: turn off rewritten by the optimizer on the prompts you have settled, run, then move on to the next.
